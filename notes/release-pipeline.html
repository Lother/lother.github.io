多 repo 發版管線的四個設計決策

維運 100 多個 repo 的建置、發版和同步，靠的不是多寫程式，而是把「會靜默壞掉的地方」一個個找出來。

Lother Guo・技術筆記

背景

這套管線服務一組 70 多個 C# 開源專案的在地化分支，加上它們依賴的函式庫，總共 100 多個 repo。每個專案各自有 GitHub Actions 建置和 release，另外有一個「索引 repo」彙整所有專案的最新版本資訊（一份 JSON feed），讓使用者用一個網址就能拿到全部更新。

管線由 Python 腳本（約 4,700 行，含單元測試）和 GitHub Actions 組成。實作由 AI coding agent 完成，需求、架構、審查與每次事故的裁決則由人負責。以下整理其中四個決策。

1. 發版從「同步等待」改成「推完就走」

問題

原本的發版腳本是同步的：推 tag、觸發 release workflow，然後原地等 CI 建置完成、等 release 出現，再更新 feed。一個專案要 60～190 秒，一輪十幾個版本就是半小時的空窗，而這半小時純粹在等 GitHub。

決策

把職責拆開：

  1. 本機腳本只負責推 tag 並觸發 release，秒級返回
  2. 各專案的 release workflow 負責建置與發佈
  3. 索引 repo 上的排程 workflow（每 15 分鐘）掃描各專案的最新 release，有差異才 commit 更新 feed

為什麼不用跨 repo 事件（repository_dispatch）

即時性更好，但要在 100 多個 repo 裡各放一把能寫入索引 repo 的權杖當 secret。因此定下一條紅線：不再新增任何 PAT。排程只需要一個身分，憑證面積小得多；代價是最多 15 分鐘的延遲，對這個場景完全可以接受。

保留退路

舊的同步行為留成 --wait 旗標，排程壞掉時可以手動補。順手修掉一個舊缺陷：舊版只改檔不 commit，「版本上線了但 feed 看不到」是零徵兆的失敗。

2. 失敗分級：一個專案的暫時錯誤，不該擋住所有人

事故

第一版的偵測很嚴格：log 裡只要出現任何 [FAIL]，整個 run 就失敗、不寫入 feed。某天晚上 GitHub 平台出事故，單一專案的 API 暫時錯誤讓整輪失敗，其餘 50 多個已經建好的 release 全部沒能進 feed。

反過來，最早的版本更糟：逐專案 catch 例外、印一行錯誤後照樣以 0 離開，run 永遠是綠的，失敗完全被吞掉。

決策

分級由同步腳本自己判斷，workflow 只看離開碼：

離開碼情況處理
0成功，可能帶警告失敗的專案沿用 feed 裡既有的條目，下一班自動重試
2全部專案都失敗判定為平台級問題，硬失敗
2feed 檔寫入失敗硬失敗
2失敗的專案在 feed 裡沒有舊條目可沿用硬失敗：新專案首發不能被靜默漏掉
2分級邏輯本身遇到未預期狀態當作硬失敗，不吞

另外把警告計數寫在 run summary 最上面，每筆警告送一則 annotation，讓「成功但有警告」和「全綠」一眼就分得出來。分級規則有獨立的單元測試。

原則：能降級就降級，但每一種「可能讓人永遠不知道」的失敗都必須是硬失敗。

3. 憑證最小化與 fail-closed 的防洩漏檢查

  • 用 GitHub App 取代個人權杖：發版和同步都用 App 換來的短期 installation token，run 的執行者顯示成 bot 而不是個人帳號。App 私鑰同時支援「PEM 內容」（CI 的 secret）和「檔案路徑」（本機）兩種形狀，以開頭字串分辨，兩種都有內建自測。
  • 上傳前的防洩漏檢查：要上傳的 zip／gzip 先掃過一遍，找到不該出現的帳號痕跡就不上傳。要找的字詞只存在 repo 以外的本機檔案，原始碼和 workflow 裡都不含它；讀不到設定就一律不放行（fail-closed），錯誤訊息只印長度、不印內容。另外也規定比對規則（只認字詞開頭、限定三種大小寫形式），降低誤判。

4. 轉 private 時的兩個靜默陷阱

後來整組 repo 要從 public 轉成 private。排程 workflow 的邏輯完全不用改，但盤點「哪些假設只在 public 時成立」之後，找到兩個會讓管線不報錯、不顯示失敗、就是永遠不再更新的陷阱：

(a) Self-hosted runner 不接 public repo 的工作

轉 private 後，GitHub-hosted runner 會開始吃組織的免費額度：每 15 分鐘一次，一個月 2,880 個 run，會直接打爆每月 2,000 分鐘的額度，所以改用 self-hosted runner。但 runner group 預設 allows_public_repositories=false：只要索引 repo 還是 public，job 就會永遠排在 Queued，沒有任何錯誤。

(b) 組織 secret 只對 private repo 可見

App 私鑰存成組織層級的 secret，能見度設定是「只給 private repo」。索引 repo 還是 public 的那段時間，workflow 裡讀到的是空字串，腳本退回本機登入身分，而 runner 上根本沒登入過。

決策

這兩條是硬相依，所以 workflow 的修改必須和「索引 repo 轉 private」同一批生效，不能提前推。這種沒有任何錯誤訊息會主動找上人的失敗，只能靠事前盤點擋下來。

附記：卡死的 workflow

有一次 workflow 被觸發後永遠停在 queued、無法取消，連以前跑成功的舊 commit 也一樣。依序排除了 concurrency group、runner 本身（同一台 runner 上別的 repo 正常）、組織 Actions 政策，以及關掉再重開 Actions，全部無效。時間點對應到剛剛批次刪除了這個 workflow 的 600 個歷史 run。

最後的修法是：GitHub 用檔案路徑識別 workflow，而不是 name: 或內容。把檔案改名就等於建立一個全新的 workflow 實體，繞開壞掉的舊實體；邏輯逐字不變。

心得

  • 自動化最大的風險不是「會報錯的失敗」，而是靜默的失敗。每個設計都先問：「這裡壞了，會有人知道嗎？」
  • 每次事故都寫成紀錄：症狀、排除過的原因、修法、為什麼這樣修。之後的決策都以這些紀錄為依據。
  • 以 AI agent 開發時，人的工作重心在定義紅線、拆解需求、審查設計，以及判斷「這個錯誤該降級還是該擋」。這些判斷沒辦法交給 AI。
